# Personal Reflection: Session 7 – Java Artifacts, Automated Builds, and Text Encoding

**Session Date:** 27/08/26  


---

## What I Learned & Key Takeaways

In this session, we examined how Java code moves through the build pipeline into production-ready software. Tracking the progression from `.java` source files to `.class` bytecode, and finally into a packaged `.jar` archive, clarified the entire build lifecycle.

A key insight was repository hygiene. Committing compiled files causes repository bloat, merge conflicts, and environment bugs. The rule is simple: track `.java` files and `pom.xml` in Git, but keep the `target/` folder and `.class` outputs in `.gitignore`.

Maven uses `pom.xml` as a blueprint to manage compiling, testing, and packaging via plugins like `maven-jar-plugin`. This integrates directly into CI/CD pipelines (e.g., GitHub Actions), which run `mvn compile` and `mvn test` automatically on every push to verify code stability.

Finally, we covered character encodings. UTF-8 uses 1 byte for standard ASCII characters, making it ideal for web efficiency, while UTF-16 uses a 2-byte minimum, making it more efficient for CJK scripts and serving as Java's internal string representation.

---

## Core Takeaways

* **Repository Cleanliness:** Commit source code (`.java`) and build blueprints (`pom.xml`); exclude generated bytecode and JARs to avoid build conflicts.
* **Automated Builds:** Maven uses `pom.xml` to standardize compiling, testing, and packaging across developer environments.
* **CI/CD Integration:** Continuous integration pipelines build and test code automatically on every push to catch bugs early.
* **Text Encoding Trade-offs:** UTF-8 optimizes ASCII text and web standards, whereas UTF-16 optimizes multi-byte language scripts and Java runtimes.
